# Resource schemas

Ferrum Edge's Admin API resource request schemas, published as self-contained
JSON Schema 2020-12 documents. Each `<Component>.schema.json` holds one
component of Edge's `openapi.yaml`, plus every component it references, under
`$defs`. The `openapi.yaml` is the exact file the plugin catalog pins
(`config_schema_document`). The components are:

| File | Edge component | Used for |
|---|---|---|
| `ProxyCreate.schema.json` | `components.schemas.ProxyCreate` | `POST /proxies` request bodies |
| `UpstreamCreate.schema.json` | `components.schemas.UpstreamCreate` | `POST /upstreams` request bodies |
| `ConsumerCreate.schema.json` | `components.schemas.ConsumerCreate` | `POST /consumers` request bodies |
| `PluginConfigCreate.schema.json` | `components.schemas.PluginConfigCreate` | `POST /plugins/config` request bodies, with every plugin's config conditional from `PluginConfigBase` |
| `GatewayTrustBundleCreate.schema.json` | `components.schemas.GatewayTrustBundleCreate` | `POST /gateway-trust-bundles` request bodies |

Each `$id` names the Edge release it was generated from
(`.../resource-schemas/edge-<ref>/<Component>.schema.json`), and `x-generated`
records the source file, commit, SHA-256 and pointer. These files are
generated by `ci/plugin_config_schemas.py`, together with
[`plugin-config-schemas/`](../plugin-config-schemas). Never edit them by hand.
`ci/validate.py` checks them against the 2020-12 meta-schema and the catalog's
pin, and, with `--fetch-openapi`, byte for byte against the generator output
for the pinned file. Every reference is resolved before a file is written.

These are Edge's own API schemas, bound to the Edge release the catalog pins
and governed by Edge's support policy, not schema majors of this repository
([versioning.md](../docs/versioning.md#stability-promise-for-contracts-edge-1),
rule 5).

## Rules that are not in these schemas

Edge also applies admission rules that exist only in its Rust code. A document
that passes one of these schemas can still be refused by Edge. A product that
writes Edge resources must check them against a real Edge; the table says
which consumer job does so against Edge `main`.

| Rule (Edge source at the pinned tag) | What it decides | Who mirrors it, and the check against Edge `main` |
|---|---|---|
| `wildcard_matches`, `hosts_overlap` and `ambiguous_path_host_overlap` (`src/config/types.rs`) | Whether two proxies' wildcard hosts and listen paths overlap, so a route conflict is refused | ferrum-migration (`tests/helpers.py`, `src/ferrum_migration/ferrum.py`): its Edge Main Drift job runs every fixture's output through Edge `main`'s `ferrum-edge validate` and acceptance suite. ferrum-edge-git-forge-ops: its Edge Main Drift job runs `gitforgeops validate` and the lifecycle suite on the Edge `main` binary. ferrum-alloy: its Edge Main Drift job runs `ferrum-edge validate` on its generated configuration |
| `Proxy::effective_scheme` (`src/config/types.rs`) | The backend scheme Edge derives for a proxy when it is not stated | ferrum-edge-git-forge-ops (`src/plugin_catalog.rs`) mirrors it, but no job checks the omitted-scheme case: its lifecycle fixtures state `backend_scheme` explicitly, and its assembler fills an omitted HTTP-family scheme before sending (`normalize_proxy_backend_schemes`), so Edge `main` never derives one in that suite. Uncovered |
| `canonicalize_policy_path` (`src/policy_path.rs`) | The canonical form of a policy path that Edge compares and stores | ferrum-alloy (`crates/ferrum-alloy-edge/src/policy_path.rs`): its Edge Main Drift job submits the exported agent-tool document to Edge `main`'s `POST /api-specs`, which exercises the paths that document uses; no job compares the rule itself |
| `validate_fields` and other cross-field and cross-resource checks (`src/config/types.rs`, `src/config/gateway_trust.rs`) | Rules that span several fields or resources, such as ID and listen-path uniqueness, that JSON Schema cannot express | Each writer's Edge Main Drift job above, through Edge's real admission pipeline |
